# 2026-11-16 오후 결과 — Apple GPU 드라이버로 Windows 바탕화면 표시, 속도 개선

## 결론

- **맥미니(J274)에서 Windows 바탕화면이 Apple GPU 드라이버(render-admission KMD + Mesa UMD)를 거쳐 표시됨.** 콘치님이 눈으로 확인했습니다. DWM이 Apple UMD를 불러 쓰고, 디스플레이 장치는 Apple AGX 하나뿐입니다.
- 검은 화면의 원인은 DWM의 새 출력 방식(DDisplay)이었습니다. `HKLM\SOFTWARE\Microsoft\Windows\Dwm` `DisableDDisplay`=1로 해결했습니다. 원본 windows-on-m1도 같은 값을 씁니다.
- 끊김(콘치님 체감 30프레임 미만)의 원인은 두 가지였습니다. ① 화면 복사(1장 8MB)를 인터럽트 처리 수준에서 했습니다. ② GPU 메모리를 읽는 속도가 느렸습니다. ①은 고쳤고(복사 스레드), ②는 CPU 여러 개로 나눠 복사해서 줄였습니다(2749판, 실기기에서 자동 선택 결과는 아직 확인 전).

## DWM 검은 화면

| 항목 | 내용 |
|---|---|
| 현상 | DWM이 약 7초마다 0x889800d0으로 종료, 화면 검음 |
| 직접 원인 | dwmcore `CDDisplayRenderTarget::Present` → `COverlayContext::Present` → UMD `PresentMultiplaneOverlay1`이 E_NOTIMPL → `CD3DDevice::GetPresentError`가 고른 번호로 즉시 종료 |
| 확인 방법 | Microsoft 공식 심볼 서버의 dwmcore.dll(10.0.26100.7920, 크기 3971584)과 PDB로 역어셈블 |
| 해결 | `DisableDDisplay`=1 → DWM이 예전 출력 방식 사용, 충돌 0회 |

## 화면 복사 속도 (1920x1080, 1장 8MB)

| 판 | 조건 | 1장 복사 평균 (ms) |
|---|---|---|
| 2747 | 캐시 안 씀, CPU 1개 | 33.4 |
| 2747 | 캐시 씀, CPU 1개 | 25.9 |
| 2748 | 캐시 씀, CPU 1개 | 21.2 |
| 2748 | 읽기만 (GPU 메모리 → 중간 버퍼) | 21.4 |
| 2748 | 쓰기만 (중간 버퍼 → 화면 메모리) | 0.45 |
| 2748 | 캐시 씀, CPU 4개 | 8.9 |

- 화면 전환 함수가 불린 실행 수준은 10(인터럽트 처리 수준)이었습니다. 2746판까지는 그 안에서 복사해서, 복사하는 동안 그 CPU가 멈췄습니다.
- 2749판은 CPU 1·4·8개 방식을 128회씩 잰 뒤 가장 빠른 방식으로 고정합니다. 바탕화면이 가만히 있으면 출력이 거의 없어서, 화면을 움직여야 측정이 끝납니다.

## 알게 된 것

- [사실] 실행 중 `pnputil /restart-device`는 GPU 정리 없이 다음 시작으로 넘어가 0xC0000483으로 실패합니다. 실패한 상태에서 다시 시작하는 것, 설치 직후 시작하는 것은 정상입니다. 판을 바꿀 때는 Windows를 재시작합니다.
- [사실] 설치 전에 `G3Armed`를 넣어야 설치 직후 첫 시작이 성공합니다(2746 설치 때는 표시 없이 먼저 시작돼 실패).
- [사실] 하이퍼바이저 풀 창 경로가 GPU를 끈 뒤 죽던 것은 `backing_find`의 NULL 역참조였습니다. g248C로 고쳤지만 실기기에서는 아직 시험하지 않았습니다.
- [가설] GPU 메모리 읽기가 캐시를 써도 느린 이유: 드라이버의 다른 부분이 같은 영역을 쓰기 결합으로 맵해 두어서, Windows가 캐시 요청을 그에 맞춘 것으로 봅니다.

## 남은 일

1. 2749판 자동 선택 결과 확인(화면을 움직인 뒤 `NwSoftStats` 읽기).
2. 부팅할 때마다 GPU 켜기(`G3Armed` + 장치 재시작 예약 작업). Windows 설정을 바꾸는 일이라 콘치님 확인 뒤에 합니다.
3. 복사를 아예 없애는 방법(화면 출력 장치가 GPU 메모리를 바로 읽게 하기) 조사.
4. 실행 중 재시작 시 GPU 정리가 빠지는 원인.

## 15시 추가 — GPU 메모리 읽기가 느린 진짜 이유 (2750·2751·2752판 시작 시 시험)

| 조건 | 8MB 읽기 (ms) |
|---|---|
| 일반 RAM → RAM | 0.49 |
| GPU 메모리, 캐시 연결 / WC 연결 / 캐시 안 씀 연결 | 5.66 / 5.66 / 5.69 |

- [사실] 연결 속성을 바꿔도 같습니다. Windows가 이 영역의 캐시 요청을 반영하지 않습니다.

| CPU | GPU 메모리 읽기 (ms) | RAM 복사 (ms) | 계산 2천만 회 (ms) |
|---|---|---|---|
| 0~3 (효율 코어) | 5.7 | 0.43 | 79 |
| 4~7 (성능 코어) | 34.6 | 0.18 | 48 |

- [사실] Windows는 8개 모두 EfficiencyClass 0으로 압니다(ACPI에 코어 종류 정보 없음).
- [사실] 캐시 안 쓰는 메모리 읽기만 성능 코어에서 6배 느립니다. 실제 복사 21~33ms는 복사 스레드가 성능 코어에 올라간 경우가 섞인 값으로 봅니다(가설, 2752판 실제 복사 값으로 확인 예정).
- 2752판: 시작 때 CPU별로 재서, 가장 빠른 CPU 기준 1.5배 안인 CPU(0~3)에만 복사 스레드와 도우미 스레드를 묶습니다.

# 주변 장치(USB·화면·입력·네트워크) — windows-on-m1에서 가져올 것 (2026-11-15)

표기: **[사실]** = 파일:행으로 확인한 내용. **[가설]** = 확인하지 않은 추측. **[작성자 주장]** = 그쪽 저장소 문서에만 있고, 그쪽이 남긴 기록(로그·실험 기록)으로 뒷받침되지 않은 말.

- 그쪽 = paulsmir/windows-on-m1(MIT 라이선스). M1 맥북 에어(J313) 대상이고 칩은 우리와 같은 T8103입니다. 읽기만 했고 빌드·실행은 하지 않았습니다.
- 우리 = NWOAS. 맥미니 M1(J274), macOS 26 Tahoe 펌웨어입니다.
- 이번 조사에서는 아무것도 빌드하거나 실행하지 않았습니다. 지금 돌고 있는 맥미니 Windows도 건드리지 않았습니다. 이 문서에 나오는 내용 중 실제 기기에서 확인된 것은 하나도 없습니다.

## 1. 결론

1. **USB-A 데이터 손상의 답은 그쪽 저장소에 없습니다.** 그쪽은 USB-A 칩(FL1100)처럼 PCIe에 붙은 실제 장치를 Windows에 넘긴 적이 없습니다. USB는 칩에 들어 있는 USB-C 컨트롤러(DWC3) 하나만 씁니다. [사실]
   - 그쪽 기록 어디에도 USB 데이터 손상 이야기는 없습니다.
   - 다만 그쪽 기록도 "손상이 없음"을 보여 주지는 못합니다. 남은 증거는 장치 인식·네트워크 접속 정도이고, 큰 파일을 읽어 해시를 비교한 기록은 없습니다. 원인 모를 NTFS 기록 손상도 하나 남아 있습니다.
2. **USB-A 손상 원인 후보 순위를 다시 매겼습니다(모두 가설).**
   - 위로 올림: ① 32비트 임시 버퍼 경로. 장치가 32비트 주소만 쓰는데 4 GiB 아래에 Windows 메모리가 없으므로, 모든 전송이 이 경로를 탈 가능성이 큽니다. ② 오래된 전송 명세(TRB)를 읽어 엉뚱한 버퍼에 쓰는 경우. 9월에 본 "같은 파일의 앞부분 데이터가 들어감"과 맞습니다.
   - 그대로 둠: CPU 캐시 처리 순서 문제.
   - 내림: 주소 변환표 별칭 충돌. 코드상 데이터 버퍼에는 해당되지 않습니다.
3. **가장 먼저 할 일은 지금 돌고 있는 S232 결과를 보는 것입니다.** S232는 FL1100의 두 전송 옵션(No Snoop, Relaxed Ordering)을 모두 끈 상태로 돌고 있습니다. [사실] 여기서도 실패하면, 9월 S113(No Snoop만 끔) 결과와 합쳐 두 옵션 모두 주원인에서 뺄 수 있습니다.
4. **화면:** 그쪽의 완전한 화면 제어 코드는 J313 + macOS 13.5 펌웨어 + 내장 화면 전용입니다. 우리 HDMI·Tahoe에는 그대로 쓸 수 없습니다. [사실] 대신 "작은 화면을 큰 신호에 맞춰 늘려 내보내는" 코드는 4K 실험에 참고가 됩니다. 단, 그쪽에서 실제로 써 본 기록은 없습니다.
5. **네트워크:** 그쪽은 USB-C에 꽂은 RTL8153 유선 랜 어댑터로 1 Gbit/s, DHCP, SSH 접속까지 기록을 남겼습니다. [사실]
   - 우리 network.md도 이미 RTL8153을 1순위로 두고 있습니다. 바꿀 것은 꽂는 포트(USB-A → USB-C) 하나입니다.
   - 단, 맥미니에서 맥북 연결선을 꽂은 채로 그 USB-C 포트가 비어 있는지 먼저 확인해야 합니다. 이것은 아직 확인하지 않았습니다.
6. **입력:** 그쪽 키보드·트랙패드 드라이버(SPI 방식)는 맥미니에 해당 장치가 없어 쓸 데가 없습니다.

### 3-3. 화면

- 우리 화면 출력도 같은 disp0 블록입니다. (`dcp@231c00000`, `apple,connector-type = "HDMI-A"`, recovered-j274.dts:681, 696) [사실]
  - 그래서 스왑으로 늘려 내보내는 방식 자체는 같은 블록에 적용됩니다. [사실: 같은 블록 / 가설: 그대로 동작]
- 그쪽 HDMI용 GPIO 코드(dcp.c:761-786)는 M2의 외부 화면 설정용입니다. M1 설정에는 DP 송신부가 없습니다(display.c:49-55). 우리와는 관계없습니다. [사실]
- Tahoe 펌웨어의 메시지 배치는 13.5와 다를 것입니다. [가설] 우리 `tahoe_dcp_guest_hook.py`가 이를 이미 맞게 처리한다는 점은 이번에 **확인하지 않았습니다**. [가설]

### 3-4. 네트워크

- 그쪽: RTL8153을 USB-C에 꽂아 동작했습니다. (EXPERIMENTS.md:23458-23470) [사실]
  - WinPE에도 RTL8153 기본 드라이버가 들어 있다고 합니다. (ANS_CURRENT_STATE.md:147-150) [작성자 주장]
- 우리 network.md는 이미 RTL8153을 1순위로 두되, USB-A 포트를 전제로 합니다. (network.md:9, 17) [사실]
- 그쪽 USB-C 포트는 "m1n1 연결에 쓰지 않는 쪽 Type-C 포트"입니다. (hv_irq_routes.c:9) [사실] 맥미니에서 맥북 연결선을 꽂은 채로 이 포트가 실제로 비어 있는지는 확인하지 않았습니다.
- 내장 유선 랜(BCM57762)과 Wi-Fi(BCM4378)에 쓸 만한 것은 그쪽에 없습니다. [사실]

## 4. 옮기는 순서 (담당·검증 방법)

담당 표기: **콘치님** = 실제 맥미니 조작·결과 확인. **Claude** = 코드·로그 분석, 수정안 작성. 하이퍼바이저·UEFI를 바꾸는 단계는 빌드한 뒤 실제 기기에서 시험해야 합니다. 빌드가 되었다고 해결된 것이 아닙니다. 합격 기준은 "같은 큰 파일을 여러 번 복사해 해시가 모두 원본과 같음"입니다.

| 순서 | 할 일 | 다시 빌드 | 담당 | 검증 방법 | 결과에 따른 판단 |
|---|---|---|---|---|---|

# 갈래 5 (앞부분) — 맥북 없이 게스트 띄우기 (C 게스트 실행기) (2026-11-15)

> 이 문서는 읽기 전용 설계 조사와 그 조사의 재검증을 합친 계획서입니다. 아무것도 빌드·실행하지 않았고, 시리얼 장치(/dev/cu.*)는 열지 않았으며, 돌고 있는 게스트는 건드리지 않았습니다.
> 아래 설계는 **한 줄도 구현되지 않았고, 실제 맥미니에서 한 번도 시험하지 않았습니다.** "빌드됨"은 "부팅됨"이 아닙니다.
> 표기: **[사실]** = 파일:줄 또는 로그로 확인한 것, **[사실·재확인]** = 재검증 단계에서 다시 읽어 맞다고 확인한 것, **[가설]** = 확인하지 않은 추측, **[확인 못 함]** = 근거를 찾지 못했거나 재검증이 다시 보지 못한 것.
> 경로 줄임: `PY` = `m1n1_windows/proxyclient/m1n1/hv/__init__.py`, `C` = `m1n1-layout-s231/src/`.
> 이 문서는 `STANDALONE-CENSUS-20261115.md`(이하 "조사 문서")의 8번째 단계(이하 M8)와, 그 앞뒤로 맥북 없이 버티는 데 필요한 단계(M3~M7, M11)를 다룹니다. 시동 디스크 고르기 화면 항목·macOS 되살리기(M9~M10)는 `dualboot.md`, 화면(M12)은 `display.md`에 있습니다.

## 1. 결론

1. **지금 Windows가 켜지려면 맥북이 반드시 필요합니다. 이유는 하나입니다 — 게스트(Windows 쪽)를 띄우는 순서 전체를 맥북의 파이썬이 USB로 하나씩 명령해서 하고 있기 때문입니다.** [사실: `hv_init`·`hv_start`는 프록시 명령 P_HV_INIT·P_HV_START로만 불림 — `C/proxy.c:475-482`, 조사 문서] 이 문서의 일은 그 순서(32단계, 2장 표)를 m1n1 하이퍼바이저(이하 HV) 안의 C 코드로 옮기는 것입니다.
2. **옮길 일의 양은 크지만, 필요한 부품은 대부분 C에 이미 있습니다.** 메모리 연결(`hv_map_hw`·`hv_map_hook`), NVMe 초기화(`nvme_init`·`nvme_set_guest_map`), 게스트 시작(`hv_start`), 체인로드(`chainload_image`)가 있습니다. 새로 써야 하는 것은 (가) 이 부품들을 맥북 파이썬과 같은 순서·같은 값으로 부르는 코드, (나) 기기 설명표(ADT, 맥이 OS에 넘기는 하드웨어 목록) 고쳐 쓰기, (다) 맥북이 없을 때 "맥북에게 묻는" 상황을 C에서 대신 처리하는 장치입니다. [사실: 각 함수 위치는 2장 표]
3. **맥북 없이 켜도 이 갈래만으로는 화면이 나오지 않을 가능성이 큽니다.** 지금 화면은 맥북 파이썬(`display-s190/tahoe_dcp_guest_hook.py`)이 디스플레이 칩(DCP)을 준비해서 나옵니다. 이 일을 C로 옮기는 것은 M12(`display.md`)입니다. [가설: 맥북 없이 부팅하면 화면 없이(헤드리스로) Windows는 돌 것 — 근거는 코드 주석뿐, `tahoe_dcp_guest_hook.py:241-247`] 그래서 **실사용(모니터 보며 작업)은 M8 + M12가 함께 끝나야** 가능합니다.
4. **맥북 연결 개발 방식은 끝까지 그대로 남깁니다.** 새 C 실행기는 "맥북이 연결돼 있지 않을 때만" 켜지게 만들고, 연결돼 있으면 지금과 똑같이 파이썬이 모든 것을 합니다. S231과 지금 실행 스크립트(`layout-s231-guest-test.sh`)는 손대지 않고 되돌아갈 자리로 둡니다.
5. **가장 먼저 할 일은 "맥북 없이 버틸 수 있는가"를 싸게 확인하는 것입니다.** 큰 이식(M8) 전에, 지금 S231로 데스크톱까지 띄운 뒤 케이블을 뽑아 보는 시험(4장 3단계)이 맥북 의존이 부팅 때뿐인지, 실행 중에도 있는지를 가려 줍니다. 이 결과에 따라 3·4장 작업량이 크게 달라집니다.

### 2.2 데스크톱까지 맥북에 "물어본" 횟수 [사실]

S231 데스크톱 부팅 로그 4개(181130, 190318, 190852, 191038)를 센 결과입니다. 모두 "Jumping to entrypoint" 뒤, 첫 NS2 줄 앞에서 나옵니다.

| 로그에 찍히는 사건 | 뜻 | 1회 부팅당 횟수(번) |
|---|---|---|
| Pass | CPU 설정 레지스터 읽기/쓰기를 맥북이 대신 통과시킴 | 14 |
| Skip | CPU 설정 레지스터 쓰기를 맥북이 무시함 | 1 |
| CPUSTART W | 보조 CPU 켜기 쓰기를 맥북이 가로챔 | 14 |
| VTIMER | 가상 타이머 문의 | 0 |
| Shadow | 그림자 레지스터 문의 | 0 |
| PMUv3 | 성능 카운터 문의 | 0 |

- [사실·재확인] 191038 로그 751-832행에서 Pass 14, Skip 1, CPUSTART W 14.
- [사실] 191038 로그 830-835행에 CPUSTART 뒤 "PMGR W"(전원 관리 쓰기) 2줄이 더 있습니다. 이것이 m1n1 앞부분·UEFI·Windows 중 어디서 왔는지는 모릅니다. 그래서 C의 전원 관리 감시는 부팅 내내 켜 둬야 합니다.
- [사실] NS2는 명령마다 로그를 남기지 않습니다. 따라서 **이 로그만으로는 "다른 문의가 전혀 없다"고 말할 수 없습니다.**
- [사실] 181130 로그는 WinPE 재부팅(job-17)으로 끝납니다. 케이블을 뽑은 시험이 아닙니다.
- 지금까지 **맥북 없이 켜 본 적은 한 번도 없습니다.**

### 4.2 설계상 위험

- **디스크 손상:** 맥북 없이 재부팅·끄기를 하면 지금은 SSD 정리 명령이 나가지 않습니다(3.1표 `hv_psci.c` 행, 사실). 3단계(케이블 뽑기) 전에 이것부터 고쳐야 합니다. 디스크 GUID·GPT 확인(2.4표 25행)이 C에도 있어야 엉뚱한 디스크에 쓰지 않습니다.
- **모르는 레지스터를 0으로 처리:** 안전하다는 근거가 없습니다(3.3, 가설). 1단계에서 실제로 걸리는 레지스터 목록을 먼저 확정하는 이유입니다.
- **파이썬 버그를 따라 할지:** CPU STATE 감시는 지금 버그 상태로 동작 중입니다(2.4). C가 "고친" 판을 만들면 지금 검증된 동작과 달라집니다.
- **전원 관리 감시의 읽기:** C 감시 함수가 읽기를 하드웨어로 넘기지 않으면 UART·USB 전원 상태를 잘못 읽어 장치가 꺼질 수 있습니다. [가설: 결과의 모양] [사실: 넘기지 않으면 자동으로 넘어가지 않음, `hv_vm.c:4068-4073`]
- **작업 규모:** "한 줄", "상수 6개" 같은 크기 추정은 모두 짐작입니다. 아무것도 빌드하거나 시험하지 않았습니다(조사 문서).
- **이 갈래만으로 실사용은 안 됨:** 화면(M12), 네트워크, 소리, GPU 가속이 다른 갈래에 남아 있습니다. 게임(리그 오브 레전드 등)은 이 갈래와 무관하게 GPU·네트워크 갈래가 먼저 필요합니다.

# USB-A 저장장치 읽기 손상 — 원인 추적과 해결 계획 (2026-11-15)

## 결론
- USB 메모리 자체는 정상이다(맥북에서 직접 읽은 지문과 wimlib 무결성 검사 통과).
- 맥미니 Windows가 USB-A(Fresco FL1100 컨트롤러)에서 파일을 **캐시를 거쳐 크게 읽을 때**, 드물게 한 번의 읽기 덩어리가 **전부 0**으로 채워진다. 버퍼 없이 1MiB씩 순서대로 읽으면(robocopy /J, NWREAD) 정상이다.
- 가장 유력한 원인(가설): USB 컨트롤러의 PCIe 설정 두 가지 — CPU 캐시를 확인하지 않는 쓰기(No Snoop)와 순서 완화(Relaxed Ordering) — 때문에, CPU 캐시에 남아 있던 0(새 페이지를 0으로 채운 흔적)이 DMA로 들어온 데이터를 덮어쓰거나, 데이터보다 완료 신호가 먼저 보인다.
- 다음 단계: 하이퍼바이저가 두 설정을 끄고 Windows가 다시 켜지 못하게 하는 S232를 만들어 같은 시험으로 확인한다.

## 관찰 (사실)
| 시험 | 결과 |
|---|---|
| USB 파일을 NWREAD로 순서대로 읽기 (WinPE, 직접 2회·일반 1회) | 정상 지문 |
| DISM을 USB에서 직접 적용 | 오류 1392 (압축 블록 손상) |
| `copy /b` USB→SSD (WinPE) | 잘못된 지문 848281b4… |
| `copy /b` SSD→SSD | 원본과 같음 (SSD 경로 정상) |
| `robocopy /J` USB→SSD | 정상 지문 c19b4892… (초당 133MB) |
| 설치된 Windows에서 `copy /b` USB→SSD 3회 | 3회 모두 aa61fd05… (2·3회는 캐시를 다시 읽은 것) |
| 같은 파일을 NUL로 복사한 뒤 USB 파일 일반 읽기 | aa61fd05… → **USB에서 캐시로 읽는 단계에서 손상** |
| 손상본과 정상본 바이트 비교 (fc /b) | 손상 구간 1개, 0x7E300000~0x7E3EFFFF, 983,040바이트, 전부 0x00 |

- 부팅마다 손상 위치와 지문이 다르다(WinPE 848281b4… / 설치된 Windows aa61fd05…). 고정된 주소 문제가 아니라 타이밍 문제 쪽이다.
- 9월 기록(STATUS-2026-09-08)에도 같은 계열의 손상이 있었다. 그때는 손상된 4KB 페이지가 같은 파일의 앞부분 데이터였다. 버퍼 처리 방식이 달라 모양만 다를 수 있다(가설).

## 원인 후보 (Opus 분석 2개 + 종합, 코드 기준)
| 후보 | 근거 | 판단 |
|---|---|---|
| H1 캐시·순서 문제 (No Snoop / Relaxed Ordering / 32비트 임시 버퍼 재사용) | 0으로 채워진 덩어리, 부팅마다 다름, 캐시 경로에서만 발생 | 가장 유력 |
| H4 오래된 전송 명세(TRB)를 읽어 엉뚱한 버퍼에 씀 | 9월 패턴과 부합 | 가능 |
| H2 하이퍼바이저의 캐시 정리 범위 | 9월에 이 정리를 빼도 실패 | 낮음 |
| H3 DART·주소 창 불일치 | 두 변환이 같은 실제 주소를 가리킴(계산 확인), 0만 나옴 | 낮음 |

- 하이퍼바이저 변경은 다시 빌드하고 다시 검증해야 한다. 빌드 성공은 해결이 아니다.

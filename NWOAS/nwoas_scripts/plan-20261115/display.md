# 화면(디스플레이) 갈래 계획 — 2026-11-15

> 표기 규칙: **[사실]** 은 파일:줄 또는 웹 주소로 확인한 것, **[가설]** 은 아직 실기로 확인되지 않은 추정입니다.
> 이 문서를 쓰면서 빌드·실행·하드웨어 시험은 하지 않았습니다. 실행 결과로 적힌 내용은 모두 기존 로그에서 읽은 것입니다.
> 빌드나 로그가 맞아도 그것만으로 성공이 아닙니다. 화면이 실제로 나오는지는 콘치님 눈으로만 확인할 수 있습니다.

## 1. 결론

1. **[사실] 지금 화면이 1280x720인 이유는 단 하나, 화면 설정 스크립트가 후보 해상도 중 1280x720을 1920x1080보다 먼저 고르도록 순위를 정해 두었기 때문입니다.** 하드웨어, 화면용 메모리 크기, UEFI 펌웨어(Project Mu) 어느 것도 720p를 강제하지 않습니다. 연결된 모니터는 1080p 60Hz와 4K 60Hz를 알려 오고 있습니다.
2. **1080p 60Hz는 스크립트 순위 한 곳만 바꾸면 시도할 수 있습니다.** 필요한 메모리는 지금 잡혀 있는 화면용 메모리(21 MiB) 안에 들어가고, m1n1·Mu·Windows를 다시 빌드할 필요가 없습니다. 다만 **이 경로로 1080p 화면이 나온 적은 한 번도 없습니다.** 따라서 이것은 "설정 하나 바꾸기"가 아니라 **"1080p 첫 화면 시험"** 으로 다뤄야 하고, 콘치님이 화면을 보고 계실 때 해야 합니다.
3. **4K 60Hz는 지금 화면용 메모리에 들어가지 않습니다.** 더 큰 화면 메모리를 새로 잡아 Windows가 쓰지 못하게 떼어 두는 작업이 필요합니다. 그 전에 "4K 신호를 내보내되 그림은 1080p로 그려 확대하게 하는" 싼 실험을 먼저 해 볼 수 있지만, 이것은 아무도 해 본 적 없는 [가설]입니다.
4. **Windows 안에서 해상도 바꾸기, 모니터를 뺐다 꽂았을 때 복구하기는 Windows용 화면 드라이버를 새로 만들어야** 가능합니다. 지금 쓰는 Windows 기본 화면 드라이버는 해상도를 바꿀 수 없다고 Microsoft가 문서로 밝히고 있습니다. 이 드라이버는 큰 작업이며, 게임용 GPU 가속 갈래의 첫 단계이기도 합니다(대체물은 아닙니다).
5. 추천 순서: ① 1080p 첫 시험 → ② 4K 확대 실험 → ③ (②가 안 되면) 4K용 큰 화면 메모리 → ④ 화면 제어 코드를 하이퍼바이저 안으로 옮긴 뒤(맥북 없는 부팅에도 어차피 필요) Windows 화면 드라이버.

## 2. 현재 상태

### 2.1 용어 풀이 (이 문서에서만 쓰는 말)

| 말 | 뜻 |
|---|---|
| 화면 설정 스크립트 | 맥북 쪽 Python 파일 `nwoas_scripts/display-s190/tahoe_dcp_guest_hook.py`. Windows가 뜨기 전에 화면 해상도를 정하고 첫 그림을 띄웁니다. |
| DCP | Apple 칩 안에서 모니터 신호를 담당하는 별도의 작은 처리기입니다. |
| DART | 그 처리기가 메인 메모리를 볼 때 쓰는 주소 변환표입니다. 화면 메모리가 여기 등록돼 있어야 화면에 나옵니다. |
| 화면용 메모리 | 화면 그림 한 장을 담는 메모리 영역입니다. 지금 22,020,096 바이트(21 MiB)입니다. |
| 부팅 정보(BootArgs) | iBoot가 넘겨주는 시작 정보입니다. 해상도·한 줄 바이트 수·화면 메모리 주소가 들어 있고, Mu와 Windows가 이것을 보고 화면 크기를 정합니다. |
| GOP | UEFI 펌웨어가 Windows에게 "화면은 이 메모리, 이 크기"라고 알려 주는 표준 방식입니다. |

### 2.2 지금 해상도가 정해지는 과정 [사실]

- 실행 스크립트가 화면 설정 스크립트를 불러옵니다(`nwoas_scripts/layout-s231-guest-test.sh:76`). 파일 지문(SHA-256)을 57번 줄에 고정해 두었고(`418aeaab…`), 현재 파일 지문과 정확히 같습니다.
- 스크립트 첫머리의 1280/720 값(`tahoe_dcp_guest_hook.py:41-44`)은 기본값일 뿐입니다. 실제로는 하이퍼바이저 시작 전에 모니터가 알려 온 해상도 목록을 읽고(`:160`), 고르는 함수 `choose_timing`을 원하는 크기 지정 없이 부릅니다(`:161-162`). 그 결과로 폭·높이를 정합니다(`:163-164`).
- `choose_timing`(`:47-69`)은 비월주사가 아닌 것, 폭 1024 이상·높이 720 이상, 화면용 메모리에 들어가는 것, 50~61Hz인 것만 남깁니다. 그다음 `standard = {(1280, 720): 0, (1920, 1080): 1}`(`:60`)로 순위를 매기므로, **모니터가 720p를 알려 오기만 하면 항상 720p가 이깁니다.** 이것이 원인의 전부입니다.
- 같은 이름의 1080p 60Hz 항목이 둘 있을 때 끝 칸 값으로 동점을 가르며, 끝 칸이 (0,0)인 항목이 (64,0)보다 먼저 뽑힙니다.

### 2.6 해상도가 Windows까지 전달되는 경로 [사실]

- 화면 설정 스크립트는 하이퍼바이저 시작 전에 부팅 정보의 화면 항목을 고쳐 씁니다(`tahoe_dcp_guest_hook.py:72-95`). 화면 메모리 주소가 바뀌지 않았는지(`:84`), 메모리가 충분한지(`:85`) 확인합니다.
- Mu는 부팅 정보에서 화면 메모리 주소와 크기(한 줄 바이트 수 × 높이, 16 KiB 단위로 올림)를 읽고(`apple_silicon_platforms_mu/Silicon/Apple/AppleSiliconPkg/PrePi/AdtParser.c:66-67`), 그 범위를 캐시 없이 매핑합니다(`T810XFamilyPkg/Library/MemoryInitPeiLib/MemoryInitPeiLib.c:535-539`). 이 캐시 설정은 UEFI 단계의 것이고, Windows는 화면 메모리를 따로 다시 매핑합니다.
- Mu의 화면 드라이버(`SimpleFbDxe.c:176-232`)는 부팅 정보의 폭·높이로 **해상도 하나짜리** GOP를 만듭니다(`:216`, 최대 모드 수 1). 한 줄 바이트 수를 폭 × 4로 가정합니다(`:224`, `:228` — 스크립트와 일치). 해상도 바꾸기 요청은 아무것도 하지 않습니다(`:128-131`).
- Windows는 Microsoft 기본 화면 드라이버(Basic Display)를 씁니다. Microsoft 문서에 "UEFI 환경에서는 해상도 변경이 불가능하다"고 적혀 있습니다(출처 1).
- GOP에 해상도가 하나뿐이므로 `bcdedit`의 해상도 관련 설정(출처 4)으로도 바꿀 수 없습니다. 고를 후보가 없기 때문입니다.
- 결론적으로 **Mu와 Windows는 부팅 정보만 따라가므로, 스크립트가 1080p를 고르면 이 두 곳은 그대로 1080p를 받습니다.** Mu·Windows 쪽 코드 변경은 필요 없습니다.
- 화면에 띄우는 그림판(DCP 레이어)의 크기도 같은 폭·높이로 만들어집니다(`tahoe_dcp_guest_hook.py:195-202`). 시작 시 5초간 띄우는 색 막대(`:188-192`)는 1920 폭에서 막대당 240픽셀로 딱 나누어집니다.
- 화면 메모리의 주소 변환표(DART) 등록은 매번 실행 중에 다시 확인하며, 실패하면 Windows 진입 전에 멈춥니다(`:183-186`). 2026-09-06 기록(`NWOAS-STATUS-2026-09-06.md:369-370`)에 1080p 크기 전체가 등록돼 있었다는 확인이 있으나, 그것은 다른 부팅에서 본 것이므로 이번에 믿을 근거는 실행 중 확인(`:185-186`)뿐입니다.

### 2.8 Windows가 뜬 뒤의 화면 [사실]

- Windows 진입 후에는 맥북 쪽이 화면 처리기(DCP)를 더 이상 다루지 않고, 관련 객체를 살려 두기만 합니다(`tahoe_dcp_guest_hook.py:274-277`, `layout-s231/STANDALONE-CENSUS-20261115.md:146`).
- 예전(S158)에 모니터를 건드리자 화면이 꺼졌고, 720p로 다시 설정하는 요청은 받아들여졌지만 그림이 돌아오지 않았으며 이어서 블루스크린이 났습니다. 원인은 다른 요인과 섞여 확정되지 않았습니다(`display-s158/README.md`).

### 단계 1 — 1080p 60Hz 첫 시험 (작음)

**무엇을 하나**

- 지금 화면 설정 스크립트를 **그 자리에서 고치지 않습니다.** [사실] 로그가 아닌 파일 17개(native-s230, loader-s223, nvme-s214, firmware-s216 실행 스크립트 등)가 이 파일의 지문 `418aeaab…`를 고정하고 있어서, 원본을 고치면 그 실행 스크립트가 전부 멈춥니다.
- 대신 프로젝트에서 늘 하던 방식대로 **새 폴더(`display-sNNN`)에 사본을 만들고 사본만 고칩니다.** 새 실행 스크립트 하나만 그 사본을 가리키게 합니다.
- 사본에서 바꿀 내용(추천안): 720p를 기본값·예비로 남기고, 환경 변수로 원할 때만 1080p를 고르게 합니다.
  - 스크립트 첫머리에 `NWOAS_FB_MODE` 환경 변수(예: `1920x1080`)를 읽는 줄 추가.
  - `:161-162`의 `choose_timing(...)` 호출에 그 값을 원하는 크기로 넘김.
  - 모니터가 그 해상도를 알려 오지 않으면 자동으로 720p로 돌아갑니다. `:176`의 확인이 두 번째 호출과 결과가 같은지 지켜 줍니다.
  - (더 작은 안) `:60`의 순위만 `{(1920, 1080): 0, (1280, 720): 1}`로 바꾸는 방법도 있으나, 그러면 720p로 되돌리려면 다시 고쳐야 합니다.
- 새 실행 스크립트에 새 사본의 지문을 고정하고 `export NWOAS_FB_MODE=1920x1080`을 넣습니다.
- `display-s190/integration-manifest.json`의 `hook_sha256`(`72280f…`)은 이미 실행 스크립트의 고정값과 달라 참고용일 뿐입니다. 새 폴더의 기록에는 맞는 지문을 적습니다.
- m1n1, Mu, Windows는 다시 빌드하지 않습니다.

| 항목 | 담당 |
|---|---|
| 사본 폴더·사본 수정·새 실행 스크립트 작성 | Claude (콘치님 승인 후) |
| 지문 계산·정적 확인(문법, 오늘 해상도 목록으로 고르는 결과 계산) | Claude |
| 실기 부팅, 화면 보며 확인 | 콘치님 |

**검증 방법 (콘치님 실기에서만)**

1. 맥북 쪽 로그에 `selected timing (1, 1920, 1080, 3932160, 0, 0)`과 `… new … 7680, 1920, 1080, 32`가 찍히는지.
2. "initial"과 "post-hotplug reapply" 두 줄 모두 `mode/swap ACK`가 찍히는지.
3. **색 막대가 모니터 폭 전체를 5초간 채우는지 — 콘치님 눈으로 확인.**
4. Mu 시리얼 로그에 `SimpleFbDxe: … Width, 1920, Height 1080` 줄이 나오는지(디버그 빌드에서 이 줄이 찍히는 설정임을 `AppleSiliconPkg.dsc.inc:84`로 확인했습니다).
5. **Windows 설정 > 디스플레이에 1920x1080, dxdiag에 "Microsoft Basic Display Adapter"가 보이는지 — 콘치님 눈으로 확인.**
6. 평소 길이만큼 써 보고 720p 때와 안정성(블루스크린 등)을 비교.

로그나 빌드가 맞는 것만으로는 성공이 아닙니다. 3번과 5번을 콘치님이 직접 보셔야 합니다.

**실패하면**: Windows 진입 전에 멈추거나(메모리·주소 변환표 확인 실패), Windows는 살아 있는데 화면이 검게 나올 수 있습니다. 두 경우 모두 디스크 데이터는 건드리지 않습니다. 환경 변수를 빼면 720p로 돌아갑니다.

### 단계 2 — 4K 신호에 1080p 그림을 확대해 내보내는 실험 (작음, [가설])

- 모니터 신호는 4K 60Hz로 설정하고, 그림은 지금 메모리에 들어가는 1920x1080으로 그린 뒤, 화면 처리기에 "원본 1920x1080을 3840x2160으로 늘려 보여라"라고 요청합니다(`tahoe_dcp_guest_hook.py:200`의 8칸짜리 사각형 값에서 원본과 대상 크기를 다르게 줌).
- 성공하면 새 메모리 없이 모니터 고유 해상도 신호를 낼 수 있습니다.
- **[가설] 지금 펌웨어(Tahoe)가 원본과 대상 크기가 다른 요청을 받아들이는지 아무 근거가 없습니다.** 이 스크립트도, 상위 m1n1도 확대 기능을 쓴 적이 없습니다. 바꾸는 값이 하나뿐이라 싸게 시험할 수 있다는 점만 장점입니다.
- 단계 1이 성공한 뒤에만 합니다(1080p 그림 자체가 안 나오면 이 실험은 의미가 없습니다).

### 단계 3 — 4K용 큰 화면 메모리 따로 잡기 (중간, 단계 2가 안 될 때만)

- 상위 m1n1에 같은 일을 하는 C 코드가 있습니다(`m1n1-layout-s231/src/display.c:496-560`): 모자라면 메모리 꼭대기에서 새로 떼어 내고, 두 주소 변환표(dart-disp0, dart-dcp)에 등록하고, 화면을 바꾼 뒤 옛 주소를 정리하고, 장치 목록(ADT)의 `/vram`과 예약 메모리 항목, 부팅 정보를 고쳐 씁니다.
- **[사실] 다만 이 C 코드는 지금 펌웨어에서는 실행되지 않습니다.** m1n1의 C 화면 초기화는 이 펌웨어에서 건너뛰고(`main.c:169-172`, `STANDALONE-CENSUS-20261115.md:9,147`), C 쪽 통신 코드는 Tahoe 펌웨어의 새 메시지 형식을 거부합니다(`src/afk.c:323-329`). 그래서 이 코드는 **참고용**이고, Python 화면 설정 스크립트에 같은 절차를 새로 구현해야 합니다.
- 또 `display.c:131-132`는 "1920x1200 이하를 선호"하는 순위 규칙이지 상한이 아닙니다. 상위 코드는 여유분을 16 KiB × 24만큼 더 잡으므로(`display.c:499-500`) 4K에는 약 33.6 MB가 필요합니다.

### 단계 4 — Windows 안에서 해상도 바꾸기·모니터 재연결 복구 (큼)

- [사실] 기본 화면 드라이버는 해상도를 바꿀 수 없으므로(출처 1), WDDM 1.2 이상의 "화면 출력 전용" 드라이버가 필요합니다. Microsoft의 예제(KMDOD, 출처 2)가 출발점입니다. 펌웨어가 잡아 둔 화면을 이어받는 구조이고, 해상도 변경·재연결·모니터 정보 읽기를 그 위에 붙이면 됩니다.
- [사실] Microsoft 규칙(출처 3의 "실패" 항목): 이 드라이버가 **시작에 실패하면** 펌웨어가 설정한 화면을 쓸 수 있게 그대로 두거나 STATUS_GRAPHICS_STALE_MODESET을 돌려줘야 하며, 후자는 블루스크린이 됩니다. 시작에 성공한 뒤에는 해상도를 바꿔도 됩니다. **설계상 뜻: 화면 처리기 상태를 한 번이라도 건드린 뒤에는 시작 실패를 내면 안 됩니다.**
- 이 드라이버는 화면 처리기(DCP)와 대화해야 하는데, 지금 그 대화 코드는 맥북 쪽 Python(`tahoe_afk_link.py`)에만 있습니다.

### GPU 갈래와의 관계 [사실 + 가설]

- [사실] Apple 칩에서 화면 출력(DCP)과 3D 계산(AGX)은 서로 다른 보조 처리기입니다.

## 2. 펌웨어 분해로 확인한 것 [사실] (13.5 펌웨어 18.20.383, 파일이 곧 RAM 0x352000부터의 내용)

링 구조체(크기 0xE0, 이름 "txfl0", "txfl1"…):

| 오프셋 | 내용 |
|---|---|
| +0x01 | 이름 문자열 |
| +0x1e | 8비트, 우리 링에서는 0xFF (가설: 상대 단말 번호, 배정 안 됨) |
| +0x22 | 링 번호(2, 3) |
| +0x24 | 상태 16비트. 비트 2 = 닫힘 |
| +0x26 / +0x2c | 출발지(자기 MAC) / 목적지(공유기 주소) |
| +0x32, +0x33 | 8비트 둘, 우리 링에서는 0, 0 (가설: tid, 인터페이스 번호) |
| +0x78 | 열기·닫기 기록 구조체 포인터: 열기 시각 5개 +0x2c, 열기 횟수 +0x40, 닫기 시각 5개 +0x5c, 닫기 횟수 +0x70, 열기 이유 5개 +0x10c, 닫기 이유 5개 +0x120 |

비트 2를 켜고 끄는 함수와, 그것을 부르는 명령 분배 함수(0x38809c, 장치 함수표 0x4300c0에 등록):

| 명령 번호 | 함수 | 링을 고르는 기준 | 뜻 |
|---|---|---|---|
| 1 / 2 | 0x3861e8 | 링 +0x1e == 인자[2] | MAC 열기 / 닫기 |
| 6 / 7 | 0x386578 | 주소(인자+8) | MAC 설명 추가 / 삭제 |
| 9 / 10 | 0x3863b0 | 링 +0x33 == 인자[4] | 인터페이스 열기 / 닫기 |
| 0x14 / 0x15 | 0x38649c | 링 +0x33, +0x32 | tid 열기 / 닫기 |
| 0x1a / 0x1b | 0x3862e8 | 링 +0x22 == 인자[0] | 링 번호로 열기 / 닫기 |

신호 번호 1, 2, 6, 9, 10의 뜻은 brcmfmac `fwsignal.c:46-55`(MAC_OPEN 1, MAC_CLOSE 2, MACDESC_ADD 6, INTERFACE_OPEN 9, INTERFACE_CLOSE 10)에서 확인했습니다 [사실]. 0x14/0x15, 0x1a/0x1b의 이름은 함수 동작에서 짐작한 것입니다 [가설]. 기록에 남는 "이유"는 이 명령 번호 그대로입니다. 실기 기록의 이유 10 = 인터페이스 닫기.

## 3. 아직 모르는 것 [가설]

- 명령 9(인터페이스 열기)를 펌웨어 윗단이 아예 안 보내는지, 보내는데 링과 맞지 않는 번호로 보내는지. 링에 남는 기록은 "맞은 것"만 적히므로 구분되지 않습니다.
- 윗단(명령을 내리는 쪽) 코드는 파일에 없는 ROM(0x352000 아래 주소)에 있을 가능성이 큽니다. 파일 안에서 명령 9/10을 넣어 부르는 자리는 찾지 못했습니다.
- Linux에서 같은 닫기 100번이 오는지, 열기가 오는지.
- s273에서 함께 바뀌던 다른 두 값(3→0x10003, 그 0x470 뒤 0x618→0)이 무엇인지.

## 7. 근본 원인 후보 — 공유기 단말 항목이 "인증 완료"로 표시되지 않음 (09:20) [코드로 확인, 실기 확인 전]

s277로 칩 ROM(0~0x170000)을 꺼내 펌웨어 파일(RAM 0x352000~)과 함께 분해했습니다(ROM 파일은 `runs/`에만 두고 저장소에 넣지 않음).

닫기·열기 신호가 만들어지는 길 [사실, 분해]:

| 단계 | 주소 | 하는 일 |
|---|---|---|
| 1 | ROM 0x151074 → RAM 0x400a80으로 덮어씀 | (wlc, bsscfg, 9 또는 10, force)를 받아 인터페이스 열기/닫기 신호를 만듦. ROM의 12곳과 RAM의 2곳에서 부름(검색·채널 이동 쪽) |
| 2 | RAM 0x400a80 앞부분 | bsscfg가 STA이고(+6 == 0) 연결됐고(+0x10 != 0) +0x48 값이 1보다 크고 요청이 열기(9)이면 0x400a4c를 불러 그 결과를 신호 종류로 씀 |
| 3 | RAM 0x400a4c | 그 bsscfg의 BSSID로 단말 항목(scb)을 찾음. bsscfg +0x48의 비트 0x100이 켜져 있으면 9. 단말 항목이 없으면 9. **단말 항목 +0x1c의 비트 0x10이 꺼져 있고 bsscfg +0x2fc의 비트 0이 꺼져 있으면 10(닫기)으로 바꿈** |
| 4 | ROM 0x151484 → 0x1509b4 → RAM 0x4002a8 → 0x3b7b94 → 함수표 0x430094의 +0x2c = 0x38809c | 신호를 장치 쪽으로 넘겨 링의 닫힘 비트를 켜거나 끔 |

- 단말 항목 +0x1c의 비트 0x10은 같은 함수의 다른 가지가 비트 0x02(연결됨)를 보는 것과 Broadcom 공개 헤더의 상태 비트 배치(AUTHENTICATED 1, ASSOCIATED 2, AUTHORIZED 0x10)로 보아 "AUTHORIZED"입니다 [가설: 이름은 추정, 비트 검사 자체는 사실].
- bsscfg +0x48은 "1보다 큼"·"비트 0x100" 검사로 보아 WPA 인증 종류 값으로 보입니다 [가설].
- Linux brcmfmac는 wpa_supplicant가 포트를 열 때 `BRCMF_C_SET_SCB_AUTHORIZE`(ioctl 121, 상대 MAC)를 보냅니다(`cfg80211.c:5396-5404`, `fwil.h:59`). bcmdhd도 `WLC_SCB_AUTHORIZE`를 보냅니다(`wl_cfg80211.c:11196`). **우리 드라이버는 이 명령을 보낸 적이 없습니다** [사실, 소스 검색]. 어제의 소스 대조에서 빠진 이유: 연결 경로가 아니라 `change_station` 경로에 있습니다.
- 그래서 지금까지의 관찰이 설명됩니다: 지금 채널만 검색은 이 함수가 불리지 않아 안 멈춤, 채널을 벗어났다 돌아오면 열기가 닫기로 바뀌어 멈춤, 링을 새로 만들면 닫힘 비트가 꺼진 채 시작해 풀림 [해석].

1.0.1.18(s278): 키 설치가 끝나면 ioctl 121을 연결된 공유기 주소로 보냅니다(스위치 `ScbAuthorize`, 기본 1). 실기에서 멈춤이 사라지는지로 확인합니다.

# 와이파이 s258q(1.0.1.8) 빌드 결과와 실기 시험 순서 (2026-11-19 10:20)

## 결론
**우리 펌웨어는 Asahi Linux 사용자가 쓰는 펌웨어와 다른 빌드입니다 [사실].** 우리 꾸러미의 `atlantisb-X3.trx`는 이 맥북(macOS 27.2.1)의 `/usr/share/firmware/wifi/C-4378__s-B1`에서 복사한 18.20.511.0.7.8.207(2026-08-11 빌드)이고, Asahi 설치기는 사용자가 고른 스텁 macOS(맥미니 M1은 기본 13.5, 예전 설치는 12.3)의 복구 이미지에서 펌웨어를 꺼냅니다. 공개 기록에 남은 맥미니 M1 Linux 사용자의 펌웨어는 18.20.383.15.7.8.150이었습니다(1장).
**"Linux에서는 검색 뒤 송신이 멈추지 않는다"는 것도, "Linux에서도 멈춘다"는 것도 공개 기록에서 확인하지 못했습니다 [사실, 검색 범위는 1-3].** 그래서 펌웨어 빌드 차이(H2)는 아직 가설로 남습니다.
**s258q는 한 번의 부팅에서 시험 검색의 모양 6가지를 차례로 시험합니다 [빌드만].** `ShapeCycle=1`이면 연결 중 120초마다 드라이버가 검색하고, 판정이 하나 날 때마다 다음 모양으로 바꿉니다. 모양별로 "펌웨어가 스스로 다시 읽었는가"를 셉니다. 연결 채널을 떠나는 것이 계기인지(H3), 검색 시간이 계기인지, 검색 요청의 모양이 계기인지(H4)를 가르는 시험입니다. s258o의 고침(초인종 한 번 더 → 흐름 링 다시 만들기)은 모든 모양에서 안전망으로 남습니다(2장).
**검색 중 수백 번 오는 펌웨어 이벤트 124는 bcmdhd 번호로 WLC_E_CCA_CHAN_QUAL(채널 혼잡도 보고)입니다 [사실, bcmdhd 헤더].** Apple 펌웨어도 같은 번호를 쓰는지는 실기 기록으로 확인합니다 [가설]. s258q가 첫 이벤트의 앞 24바이트와 해석값, 검색 중 본 채널을 기록합니다.
빌드·서명·INF 검사·단위 시험 262개는 통과했고, 맥미니에서는 아직 돌리지 않았습니다 [빌드만].

## 2. s258q에서 바꾼 것 [빌드만]

결론: 새 스위치 5개는 모두 0(또는 기본값)이면 s258p와 똑같이 동작합니다. 모양은 드라이버 시험 검색(`TestConnScanSec`)에만 걸리고 Windows가 요청하는 검색은 그대로입니다.

### 2-1. 시험 검색의 모양

| 번호 | 이름 | 검색 요청 | 가르려는 것 |
|---|---|---|---|
| 0 | base | 연결 SSID 지시, 능동, 채널 목록 없음(펌웨어 전체) — s258o/p 시험 검색 그대로 | 비교 기준(지금까지 매번 멈춤) |
| 1 | foreign | 0과 같되 연결 대역의 다른 채널 하나만(5 GHz: 연결 채널이 100 미만이면 149부터, 이상이면 36부터 찾음; DFS 제외, 유효 채널 목록에 있는 것) | 연결 채널을 잠깐(기본 능동 40 ms) 떠나는 것만으로 멈추는가. s258p의 `ch2`(연결 채널 하나, 48 ms)는 스스로 풀렸음 |
| 2 | homelong | 연결 채널 하나만, 능동 머무름 3000 ms(`ShapeLongMs`) | 채널을 떠나지 않고 검색 상태만 3초 이어질 때 멈추는가(시간 대 채널 이탈) |
| 3 | wild | brcmfmac 형식의 와일드카드: `ssid_le` 비움, 채널 목록 뒤에 빈 SSID 1개, `channel_num` = 1<<16(SSID 1개, 채널 0 = 전체), 능동 (`cfg80211.c brcmf_escan_prep`, wpa_supplicant 백그라운드 검색의 n_ssids 1) | 지시 검색·SSID 위치가 계기인가 |
| 4 | passive | SSID 없음, 수동, 전체 목록 | 탐색 요청(probe) 송신이 계기인가 |
| 5 | chunks | 지시, 능동, 두 대역의 유효 채널 전부를 3개씩(`ShapeChunkN`) 따로 검색하고 사이에 약 2초(`ShapeChunkGapMs`, 2초 진단 주기가 다음 검색을 시작) | 짧게 나눠 떠나면 매번 다시 읽는가. 사이마다 흐름 링을 보고, 보낸 항목이 그대로면 그 자리에서 판정·고침 |

- 모양 2·4는 검색 시한을 12초에서 25초로 늘렸습니다.
- 모양 1·2·5를 만들 수 없으면(연결 채널 0, 채널 목록 없음) 0으로 대신하고 `fb`로 셉니다.
- 모양 5 도중 Windows 검색이 오거나 연결이 끊기면 그 차례를 버리고 `ab`로 셉니다.

### 2-4. 이벤트 124와 120 [사실은 bcmdhd 기준]

| 번호 | bcmdhd 이름(`bcmevent.h`) | 데이터 (`wlioctl.h`) |
|---|---|---|
| 124 | WLC_E_CCA_CHAN_QUAL, "CCA based channel quality report" | `cca_chan_qual_event_t`: u16 status, u16 id, u16 chanspec, u16 len, 그 뒤 id 0이면 측정 ms·혼잡 ms·초 단위 시각, id 1·2면 잡음 세기 |
| 120 | WLC_E_MSCH, "Multiple channel scheduler event" | 이번에는 수만 셈 |

- 124가 검색 중에만 몰려 온다면 "펌웨어가 채널마다 혼잡도를 재 보고한다"는 뜻이 됩니다. 기록의 `ch`(본 채널 수)가 검색한 채널 수와 비슷하면 이 해석이 맞습니다 [가설].

- 판정 가짜 기록으로 CHECK 부분 파이썬을 돌려 표가 나오는 것은 확인했습니다(맥미니 실행은 아님).

### 결과 읽는 법

끝의 `CHECK TABLE` 줄이 모양마다 `scans alive stuck idle gone err dbfix refresh abort gapstuck fallback ms_mean/max ev124/ev120 -> 읽기`를 보여 줍니다.

| CHECK TABLE의 모습 | 뜻 |
|---|---|
| `foreign`가 멈춤, `homelong`이 스스로 읽음 | 연결 채널을 떠나는 것 자체가 계기(H3). 검색 시간은 아님 |
| `foreign`가 스스로 읽음, `homelong`이 멈춤 | 채널 이탈이 아니라 검색 상태가 오래 이어지는 것이 계기 |
| 둘 다 스스로 읽음, `base`만 멈춤 | 여러 채널을 이어서 떠나는 것(긴 이탈)이 계기. `chunks`가 스스로 읽으면 "나눠 검색"으로 피할 수 있음 |
| `wild` 또는 `passive`만 스스로 읽음 | 요청 모양(지시 SSID·탐색 요청 송신)이 계기(H4) |
| `chunks`의 `gapstuck` > 0 | 짧은 검색 하나만으로도 멈춤. `NwoaShape`의 `stuckat`가 몇 번째 검색 뒤였는지 |
| 모든 모양이 `stuck every time` | 요청 모양·시간·채널과 상관없이 검색이면 멈춤. 펌웨어 빌드(H2) 시험이나 다시 만들기 유지로 감 |
| `err` > 0 | 그 모양의 요청을 펌웨어가 거절. `NwoaEscanRequest` 값 확인 |
| `win` 줄 | Windows가 요청한 검색의 판정. s258o/p와 같은 비교 기준 |
| `NwoaEv124`의 `id`가 0이고 `ch`가 검색 채널 수와 비슷 | 124는 채널마다 혼잡도 보고(bcmdhd 뜻과 같음) |

- 한 모양의 판정이 1~3번뿐이라 "한 번 스스로 읽음"은 우연일 수 있습니다. 두드러진 모양이 나오면 `TestScanShape=<번호>`로 고정하고 20분 더 확인하는 것이 다음 순서입니다.
- PASS/NOT PASS 줄은 s258o 기준(검색 8번 이상, 멈춤 0, 끊김 0, 핑 손실 1% 미만, v4=Internet)을 그대로 씁니다. 모양 5는 검색 하나를 여러 번으로 세므로 `conn_scans`가 커집니다.

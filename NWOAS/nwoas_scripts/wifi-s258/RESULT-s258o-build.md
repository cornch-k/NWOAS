## 결론
**송신 멈춤의 원인은 "연결 중 펌웨어 검색이 시작되면 칩 펌웨어가 송신 흐름 링에서 항목을 가져가는 일을 멈추고, 검색이 끝난 뒤에도 이 흐름 링을 다시 읽지 않는 것"입니다 [사실].** 검색이 끝난 뒤 드라이버가 15개를 더 올리며 매번 초인종(doorbell)을 울렸지만 펌웨어 읽기 색인은 320에서 움직이지 않았습니다. 같은 시간 제어 링과 수신 링은 정상으로 돌았고, 흐름 링을 지우고 다시 만들자 곧바로 다시 돌았습니다(1장).
**드라이버의 링 처리(커밋마다 색인 쓰기와 초인종, 호스트 메모리 DMA 색인, 4 GiB 아래 비캐시 메모리, 레지스터 위치)는 Linux brcmfmac과 같습니다 [사실, 코드 대조].** brcmfmac에도 검색 때 흐름 링을 따로 다루는 코드가 없습니다(2장). 그래서 "검색 뒤 초인종이 빠졌다", "색인 쓰기 순서가 틀렸다"는 후보는 기록으로 배제됩니다.
**펌웨어가 왜 이 흐름 링을 다시 읽지 않는지는 아직 모릅니다 [가설].** 남은 후보는 전원 절약 방식(우리 PM0, Linux 기본 PM2), 검색 중 올린 항목, 이 Apple 펌웨어(18.20.511)의 동작입니다(3장).
**s258o는 원인 자체를 없앤 것이 아닙니다.** (1) 연결 중 검색을 다시 허용하고(`ConnectedScan` 기본 0), (2) 검색이 끝나자마자 흐름 링 읽기 색인을 지켜보다가 0.3초 안에 안 가져가면 초인종을 한 번 더 울리고, 그래도 안 되면 s258n에서 효과가 확인된 "흐름 링 다시 만들기"를 곧바로 합니다. 이렇게 하면 멈춤이 12초 넘게 가지 않고 검색 끝 0.4초 안에 풀립니다 [빌드만]. (3) 매 검색 뒤 "펌웨어가 스스로 다시 읽었는가"를 세고 펌웨어 쪽 색인 사본을 기록해, 다음 실행에서 원인을 더 좁힙니다. 8초 감시는 남겨 두었고, 통과 조건은 이 감시가 한 번도 울리지 않는 것입니다.

## 2. Linux brcmfmac과 대조

결론: 링·초인종·색인 처리는 같고, 다른 것은 전원 절약 방식과 검색 채널 목록 두 가지뿐입니다.

출처: Linux `drivers/net/wireless/broadcom/brcm80211/brcmfmac/` (pcie.c, msgbuf.c, commonring.c, cfg80211.c 공개 소스) 대 `port-j274/wifi/bcm4378-wificx/src`.

| 항목 | brcmfmac (함수) | 우리 드라이버 | 판정 |
|---|---|---|---|
| 초인종을 울리는 때 | `brcmf_commonring_write_complete`가 커밋마다 `cr_write_wptr` 다음 `cr_ring_bell` (`brcmf_msgbuf_txflow`는 최대 96개마다 한 번 커밋) | `Submit`이 커밋(1개)마다 색인 쓰기 + 초인종 | 같음(우리가 더 자주) |
| 초인종 레지스터 | `brcmf_pcie_ring_mb_ring_bell`: `h2d_mailbox_0`에 1. 코어 rev ≥ 64면 `brcmf_reginfo_64`(0xA20) | PCIe2 rev 0x44(68) → 0xA20에 1 | 같음 |
| 쓰기 색인 위치 | 펌웨어가 `SHARED_DMA_INDEX`를 알리면 호스트 메모리(`brcmf_pcie_write_idx`, 16비트 쓰기, `dma_alloc_coherent`) | 펌웨어 플래그 0x78810007(DMA 색인 켜짐, 4바이트) → 호스트 메모리에 32비트 쓰기(위 16비트 0) | 값 같음 |
| 색인 메모리 | coherent DMA 메모리 | 비캐시 연속 메모리, 물리 주소 0xBFFAB000(4 GiB 아래, DART 창 안) | 같음 |
| 순서 | `writel` 앞 배리어 | `KeMemoryBarrier` 뒤 레지스터 쓰기 | 동등. 더구나 뒤이은 15번의 초인종에도 안 움직였으므로 순서 문제는 아님 [사실] |

| 검색 중 흐름 링 | `brcmf_do_escan`·`brcmf_notify_escan_complete`는 mpc만 만짐(특정 칩 quirk) | 손대지 않음 | 같음 |

## 3. 남은 후보 [가설]과 가르는 방법

| 순위 | 가설 | 가르는 방법 |
|---|---|---|
| 1 | 펌웨어가 검색 때 멈춘 이 흐름 링을 재개하지 않음(펌웨어 쪽 동작) | `record` 실행: 검색마다 판정이 "멈춤"이고 `NwoaScanFlowLog`의 `fw`(TCM에 있는 펌웨어 쪽 w 색인 사본)가 호스트 w를 따라오면 "펌웨어가 쓰기 색인은 받았지만 읽지 않음" |
| 2 | PM0에서만 생기는 경로(Linux 기본은 PM2) | `PowerSave=2`로 같은 `record` 실행(기존 스위치) |
| 3 | 검색 중 올린 항목이 계기 | `ScanTxHold=1`: 검색 중 올리지 않고 끝나고 올림 |

`fw` 값의 뜻(TCM의 ring_info 색인 포인터가 DMA 색인 모드에서도 펌웨어 사본을 가리킨다는 것)은 가설입니다. `NwoaFwIdxNow`의 제어 링 쌍(`cs host…/tcm…`)이 평소에 같이 움직이면 이 가설이 맞습니다.

| 2 (원인 좁히기) | `bash wifi-s258/run-s258o.sh record <새 .out> <새 .link> 1200` | s258o 설치된 상태에서 `ScanFlowCheck=3`(기록만) + 시험용 검색. 멈추면 s258n의 8초 감시가 되살림. 끝에 기본값으로 되돌림 |

실행 하나에 약 25~30분 걸리고, 결과는 `wifi-s258/runs/s258o-<실행>-<시각>.txt`, 끝줄 `S258O … DONE link=…`의 link와 새 실행기 .out을 다음 실행에 넣습니다. 끝에서 두 번째·세 번째 줄 `CHECK …`와 `CHECK RESULT … -> PASS|NOT PASS`가 아래 기준의 판정입니다.

### 통과 기준 (`scans` 실행, 20분)

| 항목 | 통과 | CHECK 칸 |
|---|---|---|
| 연결 중 검색 수(개) | 3 이상 | `conn_scans` |
| 송신 멈춤 | `NwoaCntTxStall` 0, `NwoaStallLog` 비어 있음 | `stall`, `stalllog=empty` |
| Windows 연결 끊기 | `3@`·`8@` 0개 | `host3`, `host8` |
| 핑 손실(%) | 1 미만 | `loss` |
| 연결 프로필 | `v4=Internet` | `W15 PROF` |

- `bad_near_scans`는 검색 구간(앞뒤 3초) 안의 핑 손실 수입니다(두 시계 차이가 1~2초라 대략). s258n에서는 검색 3.5초 동안 송신 완료가 0개였으므로, 펌웨어가 검색 중 원래 채널로 돌아와 보내지 않는다면 검색 한 번에 핑 3~4개가 빠질 수 있습니다. 검색 4번이면 약 14개(1.2%)로 1% 기준을 넘을 수 있으니, `loss`가 기준을 넘으면 `bad_near_scans`와 나머지를 나눠 보십시오.

### 결과 읽는 법

| 결과 | 판정 |
|---|---|
| `scans`에서 `refresh`·`dbfix` > 0, `stall=0`, 끊김 0 | 고침이 작동. 원인(펌웨어 미재개)은 그대로이고 매 검색 뒤 0.4초 안에 풀었다는 뜻 |
| `scans`에서 `alive`만 늘고 `stuck=0` | 이번에는 펌웨어가 스스로 다시 읽음. `record`로 재현 여부 확인 |
| `dbfix` > 0 | 초인종 한 번 더로 풀림 → 펌웨어가 검색 뒤 첫 초인종을 놓치는 쪽(s258n 기록과는 어긋나므로 시점 차이 확인) |
| `record`에서 판정 5, `fw` = 호스트 w | 펌웨어가 쓰기 색인을 받고도 안 읽음(3장 1순위) |
| `record`에서 판정 5, `fw` ≠ 호스트 w(멈춘 값) | 펌웨어가 쓰기 색인 배열을 더 가져오지 않음(흐름 링이 아니라 색인 DMA 단계에서 멈춤) |
| `stall` > 0 (`scans`) | 검색 직후 확인이 놓친 멈춤. `NwoaScanFlowLog`의 판정(6이면 확인 시간 밖)과 `NwoaStallLog`로 판단 |

## 7. 확인 안 된 것
- 맥미니에서는 아무것도 돌리지 않았습니다. 검색 직후 다시 만든 흐름 링이 매번 바로 도는지, 시험용 검색을 Windows가 문제 삼지 않는지는 실기에서만 압니다 [빌드만].
- 펌웨어가 흐름 링을 재개하지 않는 이유(3장)는 가설입니다. PM2와 검색 채널 목록 차이는 아직 시험하지 않았습니다.
- 흐름 링을 지울 때 펌웨어가 돌려준 송신이 실제로 공중에 나갔는지 버려졌는지는 모릅니다(상태값은 0).
- 시험용 검색이 도는 동안 Windows가 요청한 검색은 "장치 바쁨"으로 돌려보냅니다(s258n까지와 같은 처리). Windows가 다시 요청하는지는 확인하지 않았습니다.

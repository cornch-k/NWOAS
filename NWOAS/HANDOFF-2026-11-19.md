### 1.2 찢어짐의 원인과 해결 [사실]

- **원인:** mca-switch1 DMA 어댑터 값 `0x102048`은 TX_LSB_PAD=8입니다. 하드웨어는 24비트 값이 아래쪽 정렬로 온다고 보고 8비트를 더 밀어 올립니다. 우리 링 데이터는 이미 위쪽 정렬(32비트 msb 정렬)이라 두 번 밀려 넘쳐 감겼고, 그래서 크기와 관계없이(부팅음 포함) 찢어졌습니다.
- **근거:** Asahi `mca.c`의 `REG_DMA_ADAPTER_A` 필드 정의와 대조. 주석과 고친 줄은 `nwoas_scripts/sound-s256/audio_module.py:343-345`, `nwoas_scripts/sound-s255/beep_levels.py:141`.
- **해결:** `0x102040`(패드 0). 12:11 설치 판에서 되읽은 값 `0x40102040` [사실]. 콘치님 귀로 깨끗함 확인(12:04).
- m1n1 `speaker_amp.py`는 입력을 −63 dB로 줄여 넣어 이 문제가 드러나지 않았던 것으로 봅니다 [가설].

### 2.2 원인과 해결 근거 [사실]

1. **iBoot마다 ADT phandle 번호가 다름.** 11-15는 macOS 26 iBoot(106), 11-18은 13.5 스텁 iBoot(102). 번호는 iBoot가 ADT를 만들 때 붙이는 일련번호입니다. 해결: "두 PERST가 `/arm-io/gpio` 노드를 가리키는가"라는 구조 확인만 남기고 고정 번호 비교를 뺌(`nwoas_scripts/wifi-s257/wifi_up.py:81-89`).
2. **Windows의 BAR 매핑은 Device-nGnRnE.** Apple PCIe에 non-posted 쓰기를 보내면 SError가 납니다(Asahi 문서 `system-registers.md`). m1n1은 PCIe를 nGnRE로 매핑해서 프록시 스크립트는 괜찮았습니다. 그래서 읽기는 되고 쓰기만 매번 터졌고, 느리게 해도 같았습니다. 해결: 하이퍼바이저가 `0x6e0000000+0x900000`을 EL2 nGnRE로 대신 접근하는 BYPASS 추적기(USB-A와 같은 방식, `nwoas_scripts/wifi-s259/wifi_module.py:98-104`). 결과 SError 0.
3. **4 GiB 위 DMA는 dart-apcie0에서 안 됨.** UEFI와 공유하는 DART 표 범위 밖입니다(FL1100도 32비트로 묶여 있음). 해결: 드라이버 `DmaMode=0` = 캐시 안 하는 연속 메모리, 게스트 물리 주소 1 MiB~0xC0000000(`port-j274/wifi/bcm4378-wificx/src/driver/msgbuf.cpp:25-32`).
4. **이 펌웨어는 EAPOL을 E_EAPOL_MSG(25) 이벤트 안에 802.1X만 담아 올림.** 드라이버가 그 이벤트를 버리고 있었습니다. 해결: 이벤트에서 꺼내 헤더를 붙여 전달(`src/driver/events.cpp:143`).
5. **NIC가 Native 802.11로 잡힘.** 수신 데이터를 이더넷 형식으로 넘겨 Windows 공급자가 알아보지 못했습니다. 해결: 802.11+LLC로 전달, 1.0판부터 코드 기본값 1(`src/driver/diag.cpp:61`).
6. **드라이버 교체 때 W9(제거)를 쓰면 저장된 연결이 지워짐**(16:28). 해결: 같은 INF 이름으로 제자리 덮어 설치(00:14, `oem40.inf` 1.0.1.1 위에 이전 `oem22.inf` 1.0.1.0이 남아 있는 것 확인, `nvmeqd-s262/runs/steps-20261119-003715.txt`).

### 3.3 Cinebench 화면 원인 사슬 [사실, 기록·소스 대조]

1. **16 MiB 한도(P22):** `lifecycle.c:723`이 UMD에 일반 버퍼 최대 크기를 알리는데, 풀 창이 없으면 16 MiB(`allocation_windows.c:81-92`). `agx_win32_screen.c:114`가 그보다 크면 KMD를 부르기 전에 거절. 그런데 DXGI는 전용 메모리 약 1 GB를 알려 앱은 큰 힙을 만들려 함.
2. **풀 매핑 증명(P23, 첫 원인):** D3D12 장치 내부 객체의 CPU 매핑이 "모든 쪽이 풀(구역 3)에 있음"을 증명하는 방식(`DirectCpuPool`, `agx_d3d12_windows.cpp:1125`)으로 기본 설정. 풀 창을 끈 지금 구성(`NWOAS_AGX_POOL_IPA=0`)에서는 절대 통과 못 함. UMD 기록 `reject-cpu-pool-map hr=0x8007000e`(사유 3 = GPU 주소표에 쪽 없음) → `reject-batch` → 그 장치의 모든 버퍼가 NULL → 152.6 MiB CPU 힙이 16 MiB 예비 경로에서 E_OUTOFMEMORY. Cinebench 콘솔에 "No supported drawport type found".
3. **맥북 해상도 고정(P28):** UMD `_Blt`가 대상 사각형 0,0-2560,1600일 때만 받음. 맥미니 1920×1080 창 크기 버퍼는 E_INVALIDARG [코드]. 21:24 콘치님 지시("해상도가 바뀌어도 동작하도록 하드코딩 아닌 버전으로")에 따라 드라이버 전체에서 크기 고정값을 없앰. 일부러 남긴 숫자(D3D 텍스처 최대 8192, 보드별 블랭킹·주사율, macOS에서 잡은 2560×1600 시험 명령 묶음 등)는 PATCHES.md P28 표에 이유와 함께 있음.
4. **스테이징 표면 거부(P30, 마지막 원인):** Windows 커널(dxgkrnl)은 구형 블릿 출력을 창의 리디렉션 표면으로 옮길 때 스테이징 표면을 씀. 우리 KMD는 공유 주 화면·그림자·GDI 세 종류만 받아 108/108 거부 → 출력은 "성공"인데 화면엔 도착하지 않음. 해결: 현재 모드 형식의 선형 32비트 CPU 가시 표면(배치는 그림자 표면과 같음, 피치 16바이트 정렬).

### 8.3 원인과 해결

- **시계가 늦은 원인 [사실]:** 맥의 하드웨어 시계(RTC)는 UTC로 맞춰져 있는데, Windows는 따로 알려 주지 않으면 RTC를 현지 시간으로 읽습니다. 그래서 UTC 15:17을 한국 시간 15:17로 읽었고, 시간 맞추기 서비스도 꺼져 있었습니다.
- **해결(N2, `nwoas_scripts/net-diag/jobs/N2-clock-utc.cmd`):** `HKLM\SYSTEM\CurrentControlSet\Control\TimeZoneInformation\RealTimeIsUniversal`=1(REG_DWORD), `sc config w32time start= auto`, `w32tm /resync /force`. 부팅마다 적용됩니다.
- **고친 뒤 한 번 더 경고가 뜬 이유 [가설, 미확정]:** SmartScreen이 "서버에 못 닿음" 결과를 잠시 기억했거나, 콘치님이 연 시점이 수정보다 조금 앞섰을 수 있습니다.
- **남은 과제:** 같은 경고가 다시 뜨면 N4(`Microsoft-Windows-SmartScreen/Debug` 기록)를 읽어 실패 단계를 확인합니다. 기록은 켜 둔 상태입니다.

## Driver task report (J274 port of windows-on-m1 apple-agx)

**Outcome.** I copied the driver sources into a new folder and added a minimal J274 patch set, switched by `/p:AppleAgxBoard=J274` (or `-DAPPLE_AGX_BOARD_J274=1`). The default J313 build is unchanged. Nothing has been built for Windows yet, because this MacBook has no WDK/SDK headers. Nothing was run on the Mac mini, nothing was downloaded, and nothing was committed. Building this is not the same as a working GPU: even with these patches, J274 cannot bring the GPU up until the hypervisor work, a live ADT read and an HDMI display path are all done.

### Patches (every change is marked `NWOAS-J274 PATCH Pn`)
- **P1, new `shared/include/apple_agx_board.h`:** one place that selects the board.
  - J274 board ID 0x22 (FACT, `nwoas_scripts/logs/appark-chainload-1558.log:49`).
  - GPU region 0xbfffb8000 and handoff 0xbfff70000:
    - FACT: m1n1 maps 0x4000-byte Normal-NC ranges at these addresses (`appark-chainload-1558.log:108-109` under 13.5, `logs/usb-s159-20260909-234847.C3i6zw:68-69` under Tahoe).
    - HYPOTHESIS (high): they are the sgx gpu-region and gfx-handoff regions.
  - Shared region 0xbfff78000: HYPOTHESIS (medium); it is not in any of our logs.
- **P2/P3:** the J313 region macros in `j313_agx_g2.generated.h:90,96,98,100` and `j313_agx_abi_admission.generated.h:18,20` now take the board values.
- **P4:** the hard-coded `GpuRegionBase` check (0x9fffb8000) now uses the board value, in `shared/src/apple_agx_config_snapshot.c:49` and `apple_agx_regionc.c:133`.
- **P5a/P5b:** the hwdata profile `gpu-region-base` input bytes, and HwDataB offset 0xa78, carry the J274 value.
  - FACT: 0x9fffb8000 occurs exactly once in HwDataB, at 0xa78.
  - HYPOTHESIS (high): that offset is m1n1's `AGXHWDataB.gpu_region_base` (`initdata.py:1143,1372`).
- **P6:** new MSBuild property `AppleAgxBoard` in the render-admission KMD, the UMD and the G2 vcxproj, plus a `-Board` argument in `build-driver.ps1`.
- **P7:** `armasm64` path uses `HostARM64` when building on an ARM64 Windows host; upstream hard-codes `Hostx64`.
- **P8:** new `arm64_hypercalls_gnu.S`, a clang-syntax twin of the `.asm` (hvc #0x4d31/#0x4d32), for a macOS cross-build.
- **P9:** `/p:AppleAgxArm64Only=true` packages with a new `AppleAgxRenderAdmission.arm64only.inf` and needs no x86 WOW64 files.

There is no board-ID check inside the driver itself (FACT, grep). The 0x26 checks are in the HV (`m1n1_windows/src/hv_agx_retained_platform.c:454`) and in the profile tool (`tools/generate_agx_hwdata_profile.py:120`).

### Build/test results (this MacBook only)
- **J313 unchanged:** I preprocessed upstream and patched sources with `clang -E -P` (config_snapshot, regionc, gfx_handoff, uat_publication, render_provider, the hwdata header, the macros). All are token-identical; config_snapshot differs by one whitespace.
- **Board self-test:** `board_selftest.c` (11 static asserts) passes for both J313 and J274, with host clang (compile and run) and with Homebrew `clang-cl 23.1.5 --target=aarch64-pc-windows-msvc /W4 /WX` (syntax check). Selecting both boards triggers the intended `#error`.
- **J274 shared sources:** `-fsyntax-only` gives 0 errors. The preprocessed output shows `0xbfffb8000ULL` and the HwDataB 0xa78 write.
- **HVC assembly:** `arm64_hypercalls_gnu.S` assembles to an AArch64 COFF object; disassembly shows the correct `hvc #0x4d32` / `hvc #0x4d31` + `ret`.
- **KMD/UMD:** not compiled, because the WDK/SDK headers are missing. No upstream script or binary was executed.

### Key inventory findings (details in INVENTORY.md)
- **Display:** the production KMD refuses to start unless the UEFI framebuffer is exactly 2560x1600 with stride 10240 (`apple_agx_post_display_route.h:22-25` → `lifecycle.c:465-475`). Our GOP is 1280x720 on HDMI, so the full build stops there.
  - The firmware-qualification profile exits earlier, in platform start (`backend_platform_windows.c:8319`, called at `lifecycle.c:399`); the display stage begins at `:425`. So it can still be tested.
  - HDMI needs new HV scanout code plus KMD display code.
- **Power/performance values:** these came from the J313 ADT and are unknown for J274; they need a live ADT read under 13.5. They are kept J313, so a J274 mismatch fails safely instead of loading wrong values.
  - pstates: 7, base 1, max 6, 8 ms (`config_snapshot.c:44-48`, `regionc.c:127-140`).
  - 66 `gpu-*` inputs, HwDataA/B and the profile ID (`apple_agx_hwdata_profile.generated.h:1505,1611`).
  - RegionC words (`regionc.c:54+`).
- **Interrupts:** the production KMD takes exactly one interrupt, synthetic GSIV 889, plus 5 memory resources (`backend_platform_windows.c:2603-2662`).
  - Our vGIC maps INTID == AIC hwirq (`m1n1-usb-s233/src/hv_vgic.c:537`). Whether 889 aliases a real AIC line is unknown.
  - The SGX mailbox IRQs 575-578 match J313 (static FDT `recovered-j274.dts:565`). 563-566 and 579 are unknown.
- **HV ABI:** HVC 0x4d31/0x4d32 (`hv_guest_ipa_pa_abi.h:7-14`) and the 0x300000000 broker page (power, config, scanout +0x400, local reserve +0xD00). None of this exists in S233 (grep finds nothing).
- **Memory:** no 8 GB assumption beyond the three region bases. The local reserve size comes from the HV at runtime, up to 1 GiB.
- **ACPI:** `ACPI\APPL0002` is not in our MacMini2020Pkg DSDT.

## Independent review

## Critical review: task "driver" (port-j274/gpu/driver)

**Verdict:** I found no blocking defect. There are two low-to-medium safety gaps and two nits, listed below. The report's claims hold where I checked them. Nothing in this task can arm the GPU today.

### Re-verified (FACT)
- **Scope and originals:** `diff -rq` against `external/windows-on-m1/drivers/apple-agx` shows exactly 13 files: 10 modified and 3 new (`apple_agx_board.h`, `arm64_hypercalls_gnu.S`, `AppleAgxRenderAdmission.arm64only.inf`). This matches the report.
  - `git status` in `external/windows-on-m1` is clean, at 6c65673; the submodules are at 882985f and 4ffc474.
  - Files changed elsewhere since 20:20 belong to the usb/wifi/display tasks, not this one.
  - No build leftovers (.o, .obj) in the driver folder.
- **Licence:** `LICENSE.windows-on-m1` is byte-identical to upstream. The upstream file headers are kept. `THIRD_PARTY.md` is present. The `.S` file and the ASL draft carry the MIT attribution.
- **Self-test:** re-run with host clang `-Wall -Wextra -std=c11`. J313 returns 0 and J274 returns 0. Defining both boards hits the `#error` at `apple_agx_board.h:22`.
- **J313 unchanged:** `clang -E -P` output is token-identical for regionc, gfx_handoff, initdata_memory, uat_publication and firmware_provider. config_snapshot differs by 1 byte of whitespace.
- **HwData scan:** an offline scan of the HwData profile bytes found 0x9fffb8000 only at HwDataB+0xa78, and nothing in HwDataA. `initdata.py:1143,1372` confirms the `gpu_region_base` field.
- **Log citations:** `appark-chainload-1558.log:49` (Board-ID 0x22) and `:108-109`, plus `usb-s159…C3i6zw:68-69`, all match the report.
- **Display and resource citations:** `post_display_route.h:22-25`, `lifecycle.c:465-475` and `backend_platform_windows.c:2603-2662` match the report.
- **The guessed shared-region base is unused:** `APPLE_AGX_BOARD_SHARED_REGION_BASE` (medium hypothesis) is used by no production code. `J313_AGX_G2_SHARED_BASE` appears only in the generated header.
- **Nothing can touch hardware now:**
  - `APPL0002` is not in our DSDT, so the KMD cannot bind.
  - Under S233, an unknown HVC (#0x4d31 or #0x4d32) goes to `hv_exc_proxy` (`m1n1-usb-s233/src/hv_exc.c:2042-2060`). That stops the guest; it does not arm the GPU.

### Defects
1. **Profile identity does not depend on the board (medium, PLAUSIBLE).**
   - Under J274, the input bytes change (`apple_agx_hwdata_profile.generated.h:1606-1614`) and HwDataB+0xa78 changes (`apple_agx_hwdata_profile.h:73-78`). `AgxHwdataProfileId` (`generated.h:1505`) and the "Profile SHA-256" comment (`:32`) stay the J313 values.
   - The HV publishes that constant ID (`m1n1_windows/src/hv_agx_retained_platform.c:529`). The driver only checks that the two IDs are equal (`apple_agx_hwdata_profile.h:28`).
   - Result: an HV built for one board and a driver built for the other pass the receipt check, yet materialise different HwDataB contents.
   - Existing mitigation: the config-snapshot `GpuRegionBase` check is read at `backend_platform_windows.c:8133`, before the handoff map at `:8162`.
   - Fix: give J274 a distinct ID (for example a separate `AgxHwdataProfileIdJ274` array), or add the board ID to the receipt and check it. Mark the SHA comment "J313 only".
2. **The handoff base is not checked against live data (low).**
   - The KMD maps and writes `J313_AGX_G2_HANDOFF_BASE` (`backend_platform_windows.c:8162-8183`).
   - The only check, the resource match at `:2633`, compares it with the ACPI draft (`acpi-draft/J274AppleAgxAbiAdmission.asl.inc:51,72`), which carries the same guess. The check is therefore circular.
   - Fix: have the HV publish the ADT `gfx-handoff-base` in the config page and have the KMD compare against it, or at least require handoff == the HV-reported `GpuRegionBase` - 0x48000.
   - Keep the J274 build uninstalled until the ADT dump is done. README step 2 already says this.
3. **The armasm64 host is chosen by guess (low, HYPOTHESIS).**
   - `AppleAgxRenderAdmission.vcxproj:27-28` keys on `PROCESSOR_ARCHITECTURE`. An MSBuild running under x64 emulation reports AMD64 and would pick `Hostx64`, which may not be installed on an ARM64 machine.
   - Fix: choose with `Exists('$(VCToolsInstallDir)bin\HostARM64\arm64\armasm64.exe')`.
4. **Nit:** `apple_agx_board.h:21` raises the `#error` for `-DAPPLE_AGX_BOARD_J274=0 -DAPPLE_AGX_BOARD_J313=1` even though J274 is not selected. Test the macro values, not just `defined`.

- Honesty: the report and the docs keep build success separate from GPU success, and label every J274 value FACT or HYPOTHESIS. I found no false success claim.

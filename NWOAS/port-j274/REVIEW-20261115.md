**Key facts and hypotheses**
- FACT, J274 identity and sizes:
  - Board-ID 0x22 and Target J274 (LOG:122-123). ADT disp0.external = 1.
  - RAM end 0xbe1000000 in all 461 saved logs.
  - iBoot sizes: ADT 0x5c000, TrustCache 0x60000, SEPFW 0x59c000, preoslog 0x40000.
- FACT, phys_base drift and how the reference handles it:
  - Our natural phys_base takes 372 distinct values between 0x83b754000 and 0x83dbdc000. It comes from heap_top (hv/__init__.py:2205).
  - With the Python host, the reference pins heap_top to 0x850000000 (E/run_uefi.py:272-277).
  - Without a host, phys_base is compiled in. RAM end is clamped to min(layout, platform) (hv_autonomous_memory.c:5-22).
  - The boot stops unless the recomputed sub-layout equals the pinned values (hv_autonomous_runtime.c:216-229).
  - Draft pins 0x850000000, about 292 MiB above the highest observed base.
- FACT, reference addresses we cannot reuse:
  - The reference's emulated NVMe ECAM 0x690000000 is the real J274 apcie ECAM (ADT /arm-io/apcie reg[0]). The draft keeps our 0x700000000.
  - NVMe vINTID is also hard-coded as 64 in hv_irq_routes.h:24 (ours is 900).
  - The reference display handoff refuses external panels (display.c:837-840, dcp.c:601-604), so J274 must start with display=none.
- FACT, gaps found:
  - The reference has no hostless policy for SError/stray MSR/VTIMER traps: hv_exc_proxy is still called at hv_exc.c:2034/2036/2354/2388.
  - It has no GPT guard or write window.
  - It has no apcie pcie_init for FL1100/Ethernet/Wi-Fi.
  - Our HDMI scanout at vram 0xbe3f60000 is above RAM end; the reference standalone path does not map that range (L-4).
- HYPOTHESIS: the stage-1 m1n1 heap stays below 0x850000000. The reference has no ceiling check in hv_autonomous*.c.

**Open questions**

**Defects**
1. tools/check_j274_layout.py:166-167. The exit code ignores `reference_rule_violations` and the UINT32 PCD finding, so "exits 0" means pass even though the reference loader rejects this file and Mu cannot express a 4 GiB window.
   Fix: return nonzero on any rule violation or PCD-width finding, unless an explicit `--allow L-1` style flag is given.
2. tools/check_j274_layout.py:105-136 and J274-GUEST-LAYOUT.md. There is no carveout overlap check. MEM-14 (J274-BOARD-PROFILE.md:63) puts 20 carveout ids in 0x864000000..0x86fe38000, which is inside the draft ramdisk 0x860000000..0x8a0000000. Ids 46/47/48 (0x822400000..0x860500000) cover ADT, firmware and virtual_fb. No L-row marks this as a blocker.
   - HYPOTHESIS: this may be harmless, since the natural S231 base also falls in that span. But a coprocessor carveout (for example the NVMe/ANS one) being overwritten is the one path here that could reach macOS storage.
   - Fix: add an L-8 "carveout overlap" blocker and a checker input that takes the carveout list and reports CONFLICT.
3. README.md:65-66. `PYTHONDONTWRITEBYTECODE=1` has no effect under `-I`, because -I implies -E. The documented command therefore leaves port-j274/tools/__pycache__ behind.
   Fix: use `python3 -I -B`.
4. tests/test_check_j274_layout.py:44-47 and :85-88. These tests only compare hard-coded constants with each other and do not read the S231 log or the logs folder.
   - The first assertion is a tautology.
   - The 0x83dbdc000 maximum will go stale as logs grow.
   - Fix: parse LOG:348 and the "Physical memory:" lines from nwoas_scripts/logs read-only.
5. README.md:43 and the report. The ADT parse cannot be reproduced under `-I`, and the scratch script was deleted.
   Fix: record the exact interpreter and command, or store the extracted ADT values as JSON with the dump's sha256.
